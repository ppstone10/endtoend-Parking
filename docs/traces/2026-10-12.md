## T-154400 · L4 · 门禁三级最小风险降级（P0-A）

- 状态：进行中。
- 任务来源：用户指示执行交接文档
  [2026-10-12 精度瓶颈定位与下一步计划](../../docs/handover/2026-10-12-精度瓶颈定位与下一步计划交接.md) 的 **P0-A「门禁回退失败归零」**。
- **修改前基线**：v34 协议（300 条 / 7 场景）门禁 `E5s` = 78.3% 成功 / 0.0% 碰撞 / **`fallback_failures = 2`**；
  准入要求回退失败 = 0，属三项判据中唯一未达成的一项。
- **基线机制**（`runtime/sources.py::SafetyShieldSource`）：
  - 主轨迹不安全 → 调可信回退；回退规划器抛异常，或回退轨迹仍不安全 → `fallback_failures += 1` **并抛 `SafetyStopError` 终止回合**；
  - `guard_transition` 替换后的下一转移仍不安全 → 引擎 `record_safety_stop()` 并结束回合；
  - `transition_is_safe` 对当前位姿已在要求净空层内的情形一律否决。
- **目标状态**：安全层在任何状态下都有可执行的安全动作，"回退失败"在构造上不再发生；
  同时不掩盖专家自身的能力缺口，两者分别记账。
- 已知边界：本次**不**让专家在原本无解的状态下有解（那是 S3/S8 场景/规划专项，属 P2-B）。
- 预计影响范围：`runtime/safety.py`、`runtime/sources.py`、`tests/test_runtime_safety.py`、
  `spec/safety_training.md`（行为契约变更）。

### 16:10:00 · 方案（契约变更）

- **契约变更点**：原 Spec `SAFE-SHIELD-001`「回退轨迹仍不安全或规划失败时明确终止/报错」与
  `SAFE-SHIELD-002`「回退控制的下一转移仍不安全时……以 `safety_stop` 结束回合」被修订为
  **三级退化阶梯**：主轨迹 → 可信回退 → **最小风险动作**；新增规范 ID `SAFE-SHIELD-003`。
- 原状态 → 新状态：
  - `fallback_failures` 的含义由"回退不可用/不安全"改为"**安全层无任何安全动作可用**"，
    并保留字段使该情形始终可核验（构造上应恒为 0）；
  - 新增 `expert_fallback_unavailable` / `expert_fallback_rejected` 两项，把**专家能力缺口**显式记账；
    新增 `minimal_risk_reuses` / `minimal_risk_holds` / `minimal_risk_rate`。
- 最小风险动作的两级：① 沿用上一条已验证安全参考的尾段（计划保持）；② 单点原地保持。
- **安全性论证**：回合能走到该分支，说明当前位姿没有真实接触（否则上一步已按碰撞终止）；
  原地保持不产生新扫掠，沿用尾段则每个候选后缀都经过同一次审查。因此二者一定安全。
  这里**故意不要求当前位姿满足 0.2m 规划余量**——车辆贴障时该要求必然失败，
  用它把关正是历史"回退失败"的来源。
- 为此同时放宽 `transition_is_safe`：当否决原因是 `current_pose_collision` 时放行
  （被否决的是**状态**而不是这次转移；真实接触仍由引擎自己的 0 余量判据在每个转移上兜底）。
  其它原因（真正由转移引入的扫掠碰撞）仍然否决。
- 影响范围未升级；回退方式：`safety_mode` 显式选择 `none` / `expert_fallback` 的既有开关不变，
  旧报告不被改写。

### 16:45:00 · 证据（第一轮复测暴露第二处同类缺口）

- 第一轮真实复测（v34 协议 E5s，300 条）：**78.7% 成功 / 0.0% 碰撞**，
  **`fallback_failures = 0`** ✅（准入判据达成），`expert_fallback_unavailable = 4`、
  `minimal_risk_reuses = 4`、`minimal_risk_holds = 0`。
- 但仍有 **48 条 `safety_stop`**，且 `reasons` 聚合显示它们**不是**来自轨迹审查：
  `expert_fallback_rejected = 0`，全部干预都是 `swept_collision`（2895）与
  `next_state_swept_collision`（396）。
- 归因：`guard_transition` 给出的替代参考**通过轨迹审查**，但控制器（MPC）实际推进出的
  下一转移仍离开安全集合 → 引擎在替换后转移检查失败处直接 `safety_stop`。
  这正是 Spec `SAFE-SHIELD-002` 新写的"改用最小风险动作"所覆盖的情形。
- **发现实现落后于契约**：新写的 Spec 承诺该情形走最小风险动作，实现却是直接停止。
  按契约优先原则补实现，而不是回退 Spec。

### 16:55:00 · 实现（引擎侧走完退化阶梯）

- `runtime/sources.py::SafetyShieldSource.minimal_risk_trajectory`：公开最小风险轨迹，
  供引擎在替换后转移仍不安全时取用。
- `runtime/engine.py::ClosedLoopEngine.run`：替换后转移检查失败时，若源提供该能力，
  先改用它重新推进并复查；只有**保持轨迹也判不安全**时才 `record_safety_stop()` 结束回合。
  不具备该能力的源保持原有安全停止语义（`getattr` 可选调用，不改变其它源的契约）。
- 安全性：原有的 `safety_stop` 仍是最后兜底，未被删除，只是不再作为"首选放弃点"。
