# Train 长耗时诊断与后续调整建议

## 1. 文档目的

本文记录 2026-08-25 对当前 `train` 任务长时间无进展现象的诊断结果，说明实际执行阶段、已完成进度、主要性能限制、是否存在死循环，以及后续可采取的调整方式。

本文只保存诊断与建议，不包含本轮代码调优。

## 2. 结论摘要

当前长耗时任务实际执行的是 3000 条专家数据集构建，而不是 MineParkingNet 的神经网络 epoch 训练。

任务在检查时已经停止，不是仍在运行的死循环：

- 2026-08-25 08:04:50 检查时，系统中没有 Python 或 Conda 训练进程；
- 最后一个检查点是 `train/part-00159`，写入时间为 2026-08-25 04:49:42；
- 已完成 `train` 1600/2400 条，占 train split 的 66.7%；
- 加上尚未开始的 val 300 条和 test 300 条，整个 3000 条计划完成约 53.3%；
- 没有生成 `part-00160` 或其临时文件，因此进程是在第 161 个 train 批次完成落盘前退出或被终止。

主要速率限制是：**复杂场景中的 Hybrid A* 在单 CPU 进程中串行规划，大量任务跑满 8 秒规划上限后失败，再被最多重采 100 次。** GPU 和磁盘不是当前主要瓶颈。

## 3. 运行证据

### 3.1 已完成场景统计

根据 160 个已落盘检查点的时间和批次报告统计：

| 场景 | 已完成样本 | 耗时 | 失败重采次数 | 最慢单批次 |
|---|---:|---:|---:|---:|
| S1 | 400 | 518.6 秒 | 41 | 42.9 秒 |
| S2 | 400 | 50.0 秒 | 0 | 10.3 秒 |
| S3 | 400 | 2788.5 秒 | 250 | 403.5 秒 |
| S4 | 400 | 2073.5 秒 | 179 | 304.5 秒 |
| 合计 | 1600 | 5430.6 秒 | 470 | — |

已落盘部分的平均速度约为 17.68 条/分钟，但不同场景差异极大，不能用该平均值可靠外推剩余耗时。

S3 和 S4 共 800 条样本消耗约 81 分钟，而 S1 和 S2 共 800 条只消耗约 9.5 分钟。这说明耗时与场景规划难度和失败重采直接相关，不是样本保存或统一的数据预处理开销。

### 3.2 超时占比

已完成部分共记录 470 次失败重采，其中：

- 441 次是 `Hybrid A* 规划超时（8.0s）`；
- 29 次是未找到可行轨迹等其他规划失败；
- 规划超时占全部失败的 93.8%；
- 仅 441 次固定 8 秒超时就至少消耗 3528 秒，即 58.8 分钟；
- 这部分占已落盘总耗时 90.5 分钟的约 65%，尚未计入成功规划、碰撞检查、轨迹审计和传感器生成的时间。

### 3.3 停止位置复现

最后完成的是 S4 的第 160 个批次。按确定性任务计划，下一个批次从 `S5_crusher/T1` 开始。

对该批次原始 10 条任务进行一次受规划器自身 8 秒上限约束的复现，结果为：

- 6 条在约 8.01 秒后规划超时；
- 4 条在约 0.01 秒内成功；
- 超时任务集中在相同场景和任务层级，与历史慢批次表现一致。

这能确认停止位置立即进入了高超时批次，但不能单独证明进程最终是被人工停止、被外部环境终止，还是重试耗尽后抛出异常。精确退出原因只能从原运行终端最后的 traceback 判断，因为当前实现没有持久化未完成批次的最终异常。

## 4. 为什么看起来像死循环

没有发现无界死循环，相关循环都有明确边界：

- `planner/hybrid_astar.py::HybridAStarPlanner.plan` 的开放列表循环受 `max_planning_time_s=8.0` 和最大扩展节点数限制；
- `dataset/build.py::generate_with_retries` 使用 `range(max_retries + 1)`，默认最多尝试 101 次；
- `scripts/build_dataset.py::_build_split_in_batches` 按有限任务列表和固定 batch 遍历。

但是边界叠加后，最坏耗时仍然很长：

- 单目标任务一次规划最多约 8 秒；
- 默认每条任务最多 101 次尝试；
- 单条持续失败任务理论上可消耗约 `101 × 8 = 808` 秒，即约 13.5 分钟；
- 默认每批 10 条，只有整批生成、保存并通过严格审计后才写正式检查点；
- 单目标批次的理论最坏时间可超过 2 小时，多候选目标任务还可能更长。

因此，长时间没有新 `.npz` 文件并不表示循环无边界，更可能表示当前批次正在连续执行规划超时和重采。当前进程已经不存在，则表示这次任务最终没有继续运行。

## 5. 主要性能限制

### 5.1 首要限制：失败重采放大

`max_retries=100` 会把一个不可稳定规划的任务单元放大为最多 101 次昂贵尝试。当前 93.8% 的失败都跑满 8 秒才返回，重试策略是总耗时的最大来源。

### 5.2 单进程串行 CPU 规划

数据集构建按 split、batch、task 顺序串行执行。Hybrid A*、Reeds-Shepp 候选生成和几何碰撞检查均运行在 CPU 上，当前流程没有任务级多进程并行。

GPU 利用率不能反映本任务速度。检查时 `nvidia-smi` 没有列出 Python 计算进程；显示的 GPU 占用来自桌面或其他图形程序。当前专家数据生成算法也没有 CUDA 路径。

### 5.3 高频精细碰撞检查

当前车辆配置使用：

- `xy_resolution=0.5` 米；
- `motion_resolution=0.1` 米；
- `collision_check_resolution=0.1` 米；
- 6×3 米完整矩形外廓并包含 0.2 米碰撞余量。

Hybrid A* 每次扩展会生成多个前进、倒车和原地旋转基元，并对相邻位姿做连续扫掠检查。解析连接还会生成并检查多组候选轨迹。在复杂、狭窄或不可达场景中，大量候选最终被碰撞检测拒绝，导致 CPU 时间集中消耗在搜索和几何判断上。

### 5.4 检查点粒度影响可观察性和恢复成本

默认每 10 条样本才落一个检查点。它不会显著增加纯规划速度，但会导致：

- 批次内长时间没有文件更新；
- 进程终止时，当前批次已经完成但尚未落盘的样本全部丢失；
- 无法仅通过文件判断当前卡在批次内哪一条任务；
- 当前批次最终异常没有被独立保存。

### 5.5 神经网络训练是另一个独立问题

`scripts/train.py` 当前把设备硬编码为 `torch.device("cpu")`。这会限制后续真正的 MineParkingNet 训练速度，但不是本次 3000 条专家数据生成长耗时的原因。应在完成可用数据集后单独评估 CUDA、batch size 和数据加载策略。

## 6. 后续调整建议

### 6.1 如果只想从现有 1600 条检查点继续

保持原 seed、任务计划、车辆配置、batch size、max retries 和输出目录不变。现有实现会严格检查并跳过已经完成的批次。

根据检查点身份文件，等价续跑参数为：

```powershell
& 'D:\conda\envs\endtoend-parking\python.exe' scripts/build_dataset.py `
  --count 3000 `
  --vehicle-config configs/vehicles/tracked_drill_rig.json `
  --output data/task_dataset/tracked_v3_3000_final `
  --batch-size 10 `
  --max-retries 100
```

续跑前应先查看原终端最后的 traceback。直接续跑可以复用 1600 条结果，但不会消除 S5 及后续场景的高超时率。

### 6.2 如果允许重新建立输出目录

建议优先采用以下顺序：

1. 对每个“场景×任务类型×机动方向”先生成少量样本，记录成功率、平均规划时间和超时率；
2. 修正或排除稳定不可规划的任务单元，避免用大量重试掩盖能力矩阵与专家规划器不匹配；
3. 将 `--max-retries` 从 100 降到 5～10，使不可行单元尽快暴露；
4. 将 `--batch-size` 降到 1～5，提高进度可见性并减少中断损失；
5. 确认数据覆盖要求后，再决定是否放宽规划精度或碰撞检查分辨率。

示例参数：

```powershell
& 'D:\conda\envs\endtoend-parking\python.exe' scripts/build_dataset.py `
  --count 3000 `
  --vehicle-config configs/vehicles/tracked_drill_rig.json `
  --output data/task_dataset/tracked_v3_3000_retry10_batch1 `
  --batch-size 1 `
  --max-retries 10
```

注意：检查点身份包含 batch size、max retries、车辆模型和任务计划。改变这些参数后不能继续使用 `tracked_v3_3000_final` 原目录，必须使用新输出目录，或者先实现经过验证的检查点迁移方式。

### 6.3 中期性能优化方向

如果后续安排专门调优，建议按收益优先级考虑：

1. 在任务生成前增加快速可达性预检，尽早拒绝明显不可行的起终位姿；
2. 按场景和任务类型统计超时率，把高失败单元纳入明确的专家能力矩阵；
3. 为单条任务增加总耗时上限，而不只限制单次 Hybrid A* 调用；
4. 持久化“批次开始、当前 task ID、重试次数、最终异常”，改善停滞判断；
5. 使用多进程并行独立任务，再按确定顺序合并检查点；CPU 密集型工作优先使用进程而不是线程；
6. 对碰撞检查、解析连接频率、运动基元数量和搜索分辨率做 profiler 驱动的优化；
7. 任何降低碰撞精度或改变能力矩阵的调整，都必须重新执行轨迹可行性和机动一致性门禁。

## 7. 推荐监控指标

后续运行时至少持续输出或保存以下信息：

- 当前 split、batch、task ID 和场景/任务类型；
- 单条任务累计耗时、当前重试次数及失败类别；
- 每个任务单元的成功率、超时率和平均规划时间；
- 最近一次检查点时间与完成样本数；
- 进程 PID、CPU 使用率和内存；
- 退出异常及 traceback。

判断“卡住”的建议阈值应根据当前参数计算。例如在 `8 秒 × 101 次` 的配置下，单条任务超过 14 分钟仍未完成才接近其理论上限；但从工程效率看，不应依赖这样高的重试上限维持运行。

## 8. 最终判断

- 未发现无界死循环；
- 本次任务在检查前已经停止；
- 主要瓶颈是复杂场景 Hybrid A* 超时与 100 次重采的乘法放大；
- 第二层限制是单进程 CPU 搜索和高频精细碰撞检查；
- batch 级检查点让长重试表现得像停滞，并降低了失败定位和恢复粒度；
- 后续应先治理不可规划任务单元和重试策略，再考虑并行化与规划器微观优化；
- 真正的网络训练还需单独解决 `train.py` 的 CPU 硬编码问题。
