# Train 长耗时诊断与后续调整建议

## 1. 文档目的

本文记录 2026-08-25 对当前 `train` 任务长时间无进展现象的诊断结果，说明实际执行阶段、已完成进度、主要性能限制、是否存在死循环，以及后续可采取的调整方式。

本文只保存诊断与建议，不包含本轮代码调优。

## 2. 结论摘要

当前长耗时任务实际执行的是 3000 条专家数据集构建，而不是 MineParkingNet 的神经网络 epoch 训练。

任务在检查时已经停止，不是仍在运行的死循环：

- 2026-08-25 08:04:50 检查时，系统中没有 Python 或 Conda 训练进程；
- 最后一个检查点是 `train/part-00159`，写入时间为 2026-08-25 04:49:42；
- 已完成 `train` 1600/2400 条，占 train split 的 66.7%；
- 加上尚未开始的 val 300 条和 test 300 条，整个 3000 条计划完成约 53.3%；
- 没有生成 `part-00160` 或其临时文件，因此进程是在第 161 个 train 批次完成落盘前退出或被终止。

主要速率限制是：**复杂场景中的 Hybrid A* 在单 CPU 进程中串行规划，大量任务跑满 8 秒规划上限后失败，再被最多重采 100 次。** GPU 和磁盘不是当前主要瓶颈。

## 3. 运行证据

### 3.1 已完成场景统计

根据 160 个已落盘检查点的时间和批次报告统计：

| 场景 | 已完成样本 | 耗时 | 失败重采次数 | 最慢单批次 |
|---|---:|---:|---:|---:|
| S1 | 400 | 518.6 秒 | 41 | 42.9 秒 |
| S2 | 400 | 50.0 秒 | 0 | 10.3 秒 |
| S3 | 400 | 2788.5 秒 | 250 | 403.5 秒 |
| S4 | 400 | 2073.5 秒 | 179 | 304.5 秒 |
| 合计 | 1600 | 5430.6 秒 | 470 | — |

已落盘部分的平均速度约为 17.68 条/分钟，但不同场景差异极大，不能用该平均值可靠外推剩余耗时。

S3 和 S4 共 800 条样本消耗约 81 分钟，而 S1 和 S2 共 800 条只消耗约 9.5 分钟。这说明耗时与场景规划难度和失败重采直接相关，不是样本保存或统一的数据预处理开销。

### 3.2 超时占比

已完成部分共记录 470 次失败重采，其中：

- 441 次是 `Hybrid A* 规划超时（8.0s）`；
- 29 次是未找到可行轨迹等其他规划失败；
- 规划超时占全部失败的 93.8%；
- 仅 441 次固定 8 秒超时就至少消耗 3528 秒，即 58.8 分钟；
- 这部分占已落盘总耗时 90.5 分钟的约 65%，尚未计入成功规划、碰撞检查、轨迹审计和传感器生成的时间。

### 3.3 停止位置复现

最后完成的是 S4 的第 160 个批次。按确定性任务计划，下一个批次从 `S5_crusher/T1` 开始。

对该批次原始 10 条任务进行一次受规划器自身 8 秒上限约束的复现，结果为：

- 6 条在约 8.01 秒后规划超时；
- 4 条在约 0.01 秒内成功；
- 超时任务集中在相同场景和任务层级，与历史慢批次表现一致。

这能确认停止位置立即进入了高超时批次，但不能单独证明进程最终是被人工停止、被外部环境终止，还是重试耗尽后抛出异常。精确退出原因只能从原运行终端最后的 traceback 判断，因为当前实现没有持久化未完成批次的最终异常。

## 4. 为什么看起来像死循环

没有发现无界死循环，相关循环都有明确边界：

- `planner/hybrid_astar.py::HybridAStarPlanner.plan` 的开放列表循环受 `max_planning_time_s=8.0` 和最大扩展节点数限制；
- `dataset/build.py::generate_with_retries` 使用 `range(max_retries + 1)`；本次运行由 CLI 默认值传入 `max_retries=100`，因此最多尝试 101 次；
- `scripts/build_dataset.py::_build_split_in_batches` 按有限任务列表和固定 batch 遍历。

但是边界叠加后，最坏耗时仍然很长：

- 单目标任务一次规划最多约 8 秒；
- 默认每条任务最多 101 次尝试；
- 单条持续失败任务理论上可消耗约 `101 × 8 = 808` 秒，即约 13.5 分钟；
- 默认每批 10 条，只有整批生成、保存并通过严格审计后才写正式检查点；
- 单目标批次的理论最坏时间可超过 2 小时，多候选目标任务还可能更长。

因此，长时间没有新 `.npz` 文件并不表示循环无边界，更可能表示当前批次正在连续执行规划超时和重采。当前进程已经不存在，则表示这次任务最终没有继续运行。

## 5. 主要性能限制

### 5.1 首要限制：失败重采放大

`max_retries=100` 会把一个不可稳定规划的任务单元放大为最多 101 次昂贵尝试。当前 93.8% 的失败都跑满 8 秒才返回，重试策略是总耗时的最大来源。

### 5.2 单进程串行 CPU 规划

数据集构建按 split、batch、task 顺序串行执行。Hybrid A*、Reeds-Shepp 候选生成和几何碰撞检查均运行在 CPU 上，当前流程没有任务级多进程并行。

GPU 利用率不能反映本任务速度。检查时 `nvidia-smi` 没有列出 Python 计算进程；显示的 GPU 占用来自桌面或其他图形程序。当前专家数据生成算法也没有 CUDA 路径。

### 5.3 高频精细碰撞检查

当前车辆配置使用：

- `xy_resolution=0.5` 米；
- `motion_resolution=0.1` 米；
- `collision_check_resolution=0.1` 米；
- 6×3 米完整矩形外廓并包含 0.2 米碰撞余量。

Hybrid A* 每次扩展会生成多个前进、倒车和原地旋转基元，并对相邻位姿做连续扫掠检查。解析连接还会生成并检查多组候选轨迹。在复杂、狭窄或不可达场景中，大量候选最终被碰撞检测拒绝，导致 CPU 时间集中消耗在搜索和几何判断上。

### 5.4 检查点粒度影响可观察性和恢复成本

默认每 10 条样本才落一个检查点。它不会显著增加纯规划速度，但会导致：

- 批次内长时间没有文件更新；
- 进程终止时，当前批次已经完成但尚未落盘的样本全部丢失；
- 无法仅通过文件判断当前卡在批次内哪一条任务；
- 当前批次最终异常没有被独立保存。

### 5.5 神经网络训练是另一个独立问题

`scripts/train.py` 当前把设备硬编码为 `torch.device("cpu")`。这会限制后续真正的 MineParkingNet 训练速度，但不是本次 3000 条专家数据生成长耗时的原因。应在完成可用数据集后单独评估 CUDA、batch size 和数据加载策略。

## 6. 后续调整建议

### 6.1 如果只想从现有 1600 条检查点继续

保持原 seed、任务计划、车辆配置、batch size、max retries 和输出目录不变。现有实现会严格检查并跳过已经完成的批次。

根据检查点身份文件，等价续跑参数为：

```powershell
& 'D:\conda\envs\endtoend-parking\python.exe' scripts/build_dataset.py `
  --count 3000 `
  --vehicle-config configs/vehicles/tracked_drill_rig.json `
  --output data/task_dataset/tracked_v3_3000_final `
  --batch-size 10 `
  --max-retries 100
```

续跑前应先查看原终端最后的 traceback。直接续跑可以复用 1600 条结果，但不会消除 S5 及后续场景的高超时率。

### 6.2 如果允许重新建立输出目录

建议优先采用以下顺序：

1. 对每个“场景×任务类型×机动方向”先生成少量样本，记录成功率、平均规划时间和超时率；
2. 修正或排除稳定不可规划的任务单元，避免用大量重试掩盖能力矩阵与专家规划器不匹配；
3. 将 `--max-retries` 从 100 降到 5～10，使不可行单元尽快暴露；
4. 将 `--batch-size` 降到 1～5，提高进度可见性并减少中断损失；
5. 确认数据覆盖要求后，再决定是否放宽规划精度或碰撞检查分辨率。

示例参数：

```powershell
& 'D:\conda\envs\endtoend-parking\python.exe' scripts/build_dataset.py `
  --count 3000 `
  --vehicle-config configs/vehicles/tracked_drill_rig.json `
  --output data/task_dataset/tracked_v3_3000_retry10_batch1 `
  --batch-size 1 `
  --max-retries 10
```

注意：检查点身份包含 batch size、max retries、车辆模型和任务计划。改变这些参数后不能继续使用 `tracked_v3_3000_final` 原目录，必须使用新输出目录，或者先实现经过验证的检查点迁移方式。

### 6.3 中期性能优化方向

如果后续安排专门调优，建议按收益优先级考虑：

1. 在任务生成前增加快速可达性预检，尽早拒绝明显不可行的起终位姿；
2. 按场景和任务类型统计超时率，把高失败单元纳入明确的专家能力矩阵；
3. 为单条任务增加总耗时上限，而不只限制单次 Hybrid A* 调用；
4. 持久化“批次开始、当前 task ID、重试次数、最终异常”，改善停滞判断；
5. 使用多进程并行独立任务，再按确定顺序合并检查点；CPU 密集型工作优先使用进程而不是线程；
6. 对碰撞检查、解析连接频率、运动基元数量和搜索分辨率做 profiler 驱动的优化；
7. 任何降低碰撞精度或改变能力矩阵的调整，都必须重新执行轨迹可行性和机动一致性门禁。

## 7. 推荐监控指标

后续运行时至少持续输出或保存以下信息：

- 当前 split、batch、task ID 和场景/任务类型；
- 单条任务累计耗时、当前重试次数及失败类别；
- 每个任务单元的成功率、超时率和平均规划时间；
- 最近一次检查点时间与完成样本数；
- 进程 PID、CPU 使用率和内存；
- 退出异常及 traceback。

判断“卡住”的建议阈值应根据当前参数计算。例如在 `8 秒 × 101 次` 的配置下，单条任务超过 14 分钟仍未完成才接近其理论上限；但从工程效率看，不应依赖这样高的重试上限维持运行。

## 8. 最终判断

- 未发现无界死循环；
- 本次任务在检查前已经停止；
- 主要瓶颈是复杂场景 Hybrid A* 超时与 100 次重采的乘法放大；
- 第二层限制是单进程 CPU 搜索和高频精细碰撞检查；
- batch 级检查点让长重试表现得像停滞，并降低了失败定位和恢复粒度；
- 后续应先治理不可规划任务单元和重试策略，再考虑并行化与规划器微观优化；
- 真正的网络训练还需单独解决 `train.py` 的 CPU 硬编码问题。

## 9. 2026-08-27 优化方案与长任务执行约定

本节记录针对“专家数据生成耗时高”和“Agent 长时间监视、反复调整造成时间与额度浪费”的后续方案。2026-08-27 已实现与 split 解耦的全能力校准、case 独立硬预算、原子状态和中断恢复；正式 3000 条生成的单元熔断、整次运行预算和多进程吞吐仍待校准报告与基准验证后接入。

### 9.1 优化目标

优化目标不是让一个低效率进程尽可能久地保持运行，而是：

- 提高每 CPU 小时得到的有效专家样本数；
- 尽早识别稳定不可规划或高超时的任务单元；
- 将单任务、任务单元和整次运行的最坏耗时变成可配置预算；
- 保证中断后只损失一个微批次，并能从持久状态准确判断停止位置；
- 让长任务依赖程序自身的日志、预算和检查点运行，不依赖 Agent 高频轮询维持。

### 9.2 建议的生成流程

采用“能力校准 → 准入 → 正式生成 → 独立攻坚”的四阶段流程：

1. **能力校准：** 正式生成前，对每个“场景×任务类型×机动方向”运行少量固定 seed 样本，记录成功率、超时率、平均/P95 规划时间和失败原因。初始可用每单元 3～5 次尝试、诊断期 `max_retries=2`，使不可行单元在分钟级而不是小时级暴露。
2. **准入：** 根据校准报告生成本次运行使用的专家能力矩阵。连续超时或超时率超过配置阈值的单元进入隔离清单，不允许在正式 3000 条生成中用高重试次数掩盖；覆盖要求无法满足时应明确报告缺口，而不是静默跨单元替代。
3. **正式生成：** 只对已准入单元生成，建议从 `max_retries=5`、`batch_size=5` 起步；每次运行设置总时长预算，达到预算后在检查点边界正常退出并保留可恢复状态。
4. **独立攻坚：** 被隔离的困难单元用单独输出目录、单独 profiler 和较小样本集调优。通过同一可行性与机动门禁后再更新能力矩阵，不阻塞主体数据集生成。

现有 1600 条检查点仍可按原参数恢复，但恢复会继续承受 S5 及后续场景的高超时率。除非复用已有结果比缩短总耗时更重要，否则不建议继续用 `max_retries=100` 盲目续跑。

### 9.3 三层预算与熔断

当前只有单次 Hybrid A* 的 8 秒上限，无法阻止 100 次重采形成乘法放大。实现时应增加：

- **单任务总预算：** 统计原任务及其替代任务的累计规划时间；超过预算立即以稳定原因码失败，不再继续重采。按 8 秒单次上限，建议初始预算 30～50 秒，再根据校准数据调整。
- **任务单元熔断：** 按场景、任务类型和机动方向维护滚动成功/超时统计；达到“连续超时次数”或“最小样本数后的超时率”阈值时暂停该单元，将证据写入报告。
- **整次运行预算：** 支持最大墙钟时间或最大失败时间占比；达到预算时停止提交新任务，等待当前微批次结束并完成原子检查点。

这些预算必须写入检查点身份和 manifest，恢复时严格核对。预算触发属于可解释的受控退出，不应伪装成完整数据集。

### 9.4 检查点与可观察性

正式生成建议使用 1～5 条的微批次；诊断期用 1 条，稳定生产可先用 5 条并用基准确认审计/保存开销。除现有批次报告外，应持久化：

- 当前 split、batch、原 task ID、替代 task ID、重试次数和累计耗时；
- 每次失败的稳定原因码、单元滚动统计和预算/熔断事件；
- 最近完成检查点、进程 PID、启动参数、开始/结束时间；
- 最终状态、异常摘要和 traceback 路径。

主进程应是唯一检查点写入者；worker 只返回样本或失败结果。检查点先写临时文件、通过双门禁后原子替换，避免并行写入竞争和半成品晋升。

### 9.5 并行化顺序与边界

专家规划是 CPU 密集型工作，任务之间基本独立，适合在能力矩阵和预算机制稳定后使用进程级并行。建议：

1. 使用可配置的进程 worker 数，在当前 Windows/Python 3.12 环境按 `spawn` 方式设计；worker 入口放在可导入模块顶层，传入可序列化的任务与配置，并在 worker 初始化时复用场景组件。
2. 依次基准 1、2、4 个 worker，按有效样本/分钟、总 CPU 时间、内存和超时率选择拐点，不默认占满全部核心。
3. 结果可以乱序完成，但主进程必须按原任务序号稳定排序后生成检查点，保持 task ID、split 和固定 seed 的可复现性。
4. 不把 `Future.result(timeout=...)` 当作强制终止：已开始的 Future 不能据此取消。真正的止损依赖规划器内部截止时间、单任务累计预算和必要时可回收的独立 worker 生命周期。

不应把“降低碰撞分辨率”作为第一步。碰撞检查、解析连接频率、运动基元和搜索分辨率只在代表性慢单元上用 `cProfile` 确认累计耗时后调整，并重新通过运动学、扫掠碰撞和机动一致性门禁。

### 9.6 Agent 长任务执行协议

后续由 Agent 协助运行长任务时遵循以下约定：

1. Agent 先完成有明确时长上限的小样本校准或烟测，并给出速率、超时率、最坏任务预算和是否值得扩大运行的判断。
2. 未通过校准门禁时不启动全量生成；不在全量运行过程中一边观察一边试探性修改参数。
3. 全量任务启动后由程序自行输出进度并落盘。Agent 只在启动后确认一次“进程存在、日志增长、首个检查点成功”，之后不进行按分钟高频轮询。
4. 后续检查只在用户主动询问、程序预算触发、进程退出或到达预先约定的里程碑时进行。检查时一次性读取进程状态、日志尾部、最新检查点和失败统计，不重复收集无变化信息。
5. 判断停滞使用程序记录的“当前任务累计预算 + 合理收尾余量”，不以几分钟没有新 NPZ 文件为依据。超过预算后只做一次诊断快照，再决定受控停止或恢复。
6. Agent 不承担调度器职责。需要无人值守时，应让生成程序本身具备预算退出、状态文件和可恢复检查点；通知只汇报里程碑或最终状态，不用持续对话消耗额度维持任务。

### 9.7 实施优先级与验收

建议按以下顺序实施，上一层通过后再进入下一层：

1. 校准模式、单任务总预算、单元熔断、运行预算和持久事件记录；
2. 微批次检查点及受控退出/恢复测试；
3. 1/2/4 worker 的确定性多进程实现与基准；
4. 代表性慢单元的 profiler 驱动规划器优化。

验收至少包括：

- 配置预算触发后能够正常退出，manifest 明确标记 partial，恢复不重复或泄漏 task ID；
- 单任务耗时不超过配置总预算加一个可解释的收尾余量；
- 中断最多损失一个微批次，最终异常和当前 task ID 可从持久文件定位；
- 并行与串行使用同一任务计划，结果顺序、split、元数据和门禁口径一致；
- 与 2026-08-25 基线相比，超时重采浪费显著下降；并行化只在有效样本/分钟提高且内存可接受时启用；
- Agent 侧不再通过持续轮询维持运行，长任务状态由程序日志和检查点提供。

### 9.12 v6 几何复原与紧 bay 对齐采样（2026-08-28）

v5 正式构建在 train 第 194 批 `S3_maintenance/T3` 反复耗尽 10 次重采。逐基元诊断显示：即使把作业道加深到 20m+、去立柱、放宽净空到 0.8m、给 25s/10 万节点，T3 成功率仍只有 33–50%，全部 Reeds-Shepp/履带解析候选在远距被紧 bay 口碰撞拒绝。决定性变量是起点与目标 bay 的横向偏移：偏移 ≤1.5m 且与 bay 轴线平行时倒车 8/8 秒级成功。根因不是超时参数或栅格分辨率，而是"远距斜插进紧 bay"对欧氏启发式不可收敛，真实卡车本就先对齐再入位。

v6 阶段落地三组修复：

1. **场景几何复原**：S3 维修区按车辆相对尺度（作业道 3.5 倍车长、bay 0.6m 单侧净空、立柱与三面墙不变、spawn 与外墙保持旋转扫掠半径）；S6 岩石移出 SW 接近走廊（去岩石后 T3 12/12 秒过）；S7 加油位靠岛净空计为 `0.3m + collision_margin`（原实际仅 0.1m）；S9 破碎槽与 S5 统一为倒车入槽。
2. **紧 bay 对齐起点采样**：`TaskSampler._sample_axial_start` 对 `maintenance_bay`/`crusher_slot`/`fuel_bay` 的 T2/T3/T4/T5 起点沿 bay 轴线对齐（yaw==gyaw、按机动方向从鼻前/鼻后侧接近、横向受限）。
3. **准入方向与几何一致**：S3 全单元恢复倒车（含 T3）；S5/T2 从排除恢复为仅倒车；S9/T2、T5 仅倒车；S8/T2/T3/T5 仅前进；排除 S7/T1/T3/T5、S9/T1/T3。

验证：受影响单元 8s 扫描全部 ≥5/6（多数 6/6、毫秒级）；100 条端到端构建烟测仅 3 次失败重采；全仓 239 项测试通过。正式数据写入新目录 `data/task_dataset/tracked_pivot_v6_3000`（计划指纹变化，v4/v5 检查点与校准证据保留作旧几何归档）。
