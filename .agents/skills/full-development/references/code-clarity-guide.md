# 代码清晰度指南

仅在命名、文件拆分、注释治理是明确任务，或标准/重大变更出现具体清晰度问题时读取。

## 1. 先限定触达范围

- 列出本轮新增、实质修改或明确要求整理的声明和文件，不扫描全仓寻找风格问题。
- 区分直接要求、实现必需的局部清理和独立可维护性债务；后者单独报告或拆成后续任务。
- 遵循项目现有领域词汇、语言官方规范和格式化/静态检查配置；个人偏好不能覆盖项目约定。

## 2. 让名称在使用位置表达意图

- 类型名使用领域名词或明确角色；函数名使用动作和对象，必要时补充条件、结果或副作用。
- 布尔值表达判断，例如 `is`、`has`、`can`；转换说明方向，例如 `toDomainModel`；持久化、发送、清除等副作用必须可见。
- 弱类型参数需要说明业务角色，不能只叫 `value`、`data`、`flag`。
- 避免单独使用 `handle`、`process`、`manage`、`helper`、`util`、`wrapper`；只有调用上下文已经提供完整语义时才可保留。
- 名称无法用一句话解释，或必须依靠长注释消除歧义时，先检查声明是否承担多个职责。
- 公共 API、序列化字段、数据库列、协议名、反射字符串和跨语言桥接名称不属于普通重命名；先检查兼容、迁移和调用方。

## 3. 按职责拆文件

先为候选声明写最小映射：职责、状态所有者、依赖方向、主要调用方和建议位置。出现以下具体信号时再拆分：

- 文件存在多个独立修改原因或生命周期；
- UI、领域规则、协议映射、持久化或平台适配混在同一职责中；
- 文件名无法概括其主要内容；
- 测试某一职责必须初始化大量无关对象；
- 主要流程被大量局部辅助实现打断；
- 多人或多 Agent 经常在无关区域发生冲突。

行数只能触发调查，不能自动触发拆分。语义紧密、共同变化的声明可以留在同一文件；不要机械执行“一文件一类型”。

拆分顺序：

1. 固定公共入口、所有权和行为不变量。
2. 先移动/重命名，保持行为不变。
3. 更新 import、可见性、构建脚本、静态门禁和稳定路径引用。
4. 运行原有回归网或最小构建，证明结构调整没有改变行为。
5. 行为变化另做增量，避免差异难以审查和回退。

## 4. 只写有维护价值的注释

- 公共或跨边界声明说明用途、输入输出、错误、副作用、线程/生命周期和兼容约束。
- 实现注释解释不变量、取舍、历史兼容和“为什么不能用看似更简单的方式”。
- 不重复函数名、条件语句和赋值等表面代码；能通过清晰命名和拆函数解决时优先改代码。
- 修改行为、名称或边界时同步更新相关注释；失效注释直接删除。
- TODO 写明阻塞原因、退出条件和可定位责任边界；不保留没有行动条件的愿望清单。
- 注释扫描工具必须使用语法感知或先剥离注释，不能把 KDoc、DocC、JSDoc 中的文字误判为运行时代码。

## 5. 按风险验证重构

- 私有局部改名：检查直接引用并运行最小静态检查。
- 模块内重命名或文件拆分：运行受影响测试/编译，比较公共行为和导出符号。
- 公共 API、包、协议、数据或跨语言桥接迁移：升级到 L4，建立调用方/迁移/回退映射和 TRACE。
- 行为不变重构使用修改前后同一回归网，不制造无意义红灯。
- 只报告实际验证；IDE 重命名、搜索替换或脚本执行成功不等于行为验证通过。
