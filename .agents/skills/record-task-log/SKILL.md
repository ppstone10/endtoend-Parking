# 记录任务日志

复用本轮已有证据，在每个受影响仓库的 `docs/worklogs/YYYY-MM-DD.md` 写入一条独立任务记录。

## 1. 确定时间与文件

- 使用任务开始时已保存的本地时间；结束时只读取一次当前本地时间，不轮询。
- L2-L5 标题使用 `## T-HHmmss · HH:mm:ss–HH:mm:ss · Lx · 简短任务名`；L0/L1 由根规则写成无正文的单行二级标题。跨日任务写入结束日期文件，并在时间中保留完整开始日期。
- 当天文件不存在时创建标题 `# Agent 任务日志 · YYYY-MM-DD` 和时区；存在时先查看末尾任务标题。
- 文件自上而下必须按真实开始时间从旧到新排列。新任务通常追加到文件末尾，禁止把最新任务放到顶部；延迟补录的较早任务应移动完整任务块到正确标题之间，不改变记录事实。
- 每个任务都有自己的二级标题；不得把 L0/L1 写成前一条 L2-L5 任务正文中的普通列表项。
- 同一用户任务在完成前收到补充要求时合并为一个条目，不按对话消息拆分。

## 2. 按等级记录

### L2：局部缺陷

保留 3～5 个短项：

- 状态与结果；
- 根因和最小修复；
- 修改文件；
- 实际验证与缺口；
- 仅在确有内容时记录经验或文档影响。

### L3：标准开发

保留 5～7 个短项：

- 状态、目标和交付结果；
- 采用的方法，以及前置调研结论或跳过依据；
- 主要修改范围与文件；
- 验收和验证结果；
- 文档影响；
- 已启用 Spec 时记录规范 ID 和完成状态；
- 剩余风险或人工审查点。

### L4：重大变更

在 L3 基础上记录边界与验收、关键方案取舍、契约/数据/迁移/回退影响、多范围验证和未关闭风险。复杂证据链接 TRACE，不复制完整过程，通常不超过 10 个短项。

### L5：关键变更

在 L4 基础上记录授权、安全与隐私边界、破坏性操作、恢复方案、真实环境验证缺口和风险接受者。不能把未获授权或未完成关键验证的任务记为完整完成。

## 3. 控制日志成本

- 只写结论，不复制用户原文、完整差异、原始命令输出、网络资料全文或最终答复。
- 路径按最小有用范围列出；文件很多时记录目录或模块并链接 TRACE。
- 使用明确状态：完整完成、部分完成、受阻、仅完成诊断或无需修改。
- 日志是执行索引，不拥有当前产品、架构或使用事实，也不能代替 README、DESIGN、ARCHITECTURE、LEARNING、TRACE 或 Commit 文稿。
- 任务存在 TRACE 时，在标题或结果项使用同一 `T-HHmmss` 编号并链接当天 TRACE；不复制其修改演进。
- 日志写入本身不触发测试、构建、知识同步、TRACE 或 Commit 文稿。
- 多仓库任务在每个实际修改的仓库记录；主要仓库保留完整条目，其他仓库可写简化条目并指明关联范围。
- 写入后只检查任务标题顺序；发现倒序时调整完整记录位置，不因此重新读取实现或重复验证。
