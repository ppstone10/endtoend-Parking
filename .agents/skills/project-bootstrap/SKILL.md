# 项目初始化

建立最小且可信的项目上下文，避免反复重新发现。

## 1. 先检查，再询问

- 阅读根指令文件以及仓库清单或构建文件。
- 检查顶层目录和已有概述文档。
- 优先采用代码、配置、测试和当前行为能够证明的事实。
- 不穷举阅读实现文件，只抽查入口和边界。
- 只询问仓库无法确定的重大事实：目标、非目标、用户、不可逆约束和验收标准。
- 新项目架构、技术选型或项目内没有成熟先例的方法，遵守根 `AGENTS.md` 的前置网络调研规则；修复已有文档结构时不为形式调研。

创建或重组项目文档前，阅读 [references/document-contracts.md](references/document-contracts.md)。

## 2. 判断哪些文档确有必要

- `README.md` 用于安装、运行和用户入口，必须存在。
- 产品行为、需求、用户流程或非目标需要持久权威来源时，增加 `DESIGN.md`。
- 边界、状态所有权、数据流、协议或结构不变量不明显时，增加 `ARCHITECTURE.md`。
- 只有已经存在持久的项目特有经验时才增加 `LEARNING.md`。
- `docs/traces/YYYY-MM-DD.md` 用于复杂调查和重大变更的追加式演进跟踪；除非接入决策确需证据，否则不得仅因初始化创建空 TRACE。
- `docs/worklogs/` 按日期保存 Agent 任务执行索引；不预建空日志，也不把日志当作项目事实来源。
- 只有项目存在需要稳定规范 ID 和长期验收追溯的功能或契约时才建立 `spec/`；不要为接入工作流创建空 Spec。需要时使用 `spec-driven-change` 的模板和分级规则。
- 只有涉及真实备选方案的长期重大决策才使用 `docs/decisions/`。

`assets/` 中的模板只是起始结构，不是强制完整文档。删除无关标题，不保留占位符。

## 3. 建立权威关系与路由

- 每类持久事实只指定一个所有者。
- 解决冲突，不能把冲突复制到新文档中。
- 稳定项目事实放在概述文档，过程证据放在 TRACE。
- 项目级设计放在 DESIGN，功能级持久行为与验收放在对应 Spec，不能建立竞争的需求来源。
- 保持根 `AGENTS.md` 紧凑，将项目特有不变量放入其项目专属区。
- 根据项目真实命令定义验证阶梯，并标明哪些较广命令已覆盖较窄命令。
- 在 ARCHITECTURE 中记录稳定模块/目录职责和所有权；语言通用命名与格式优先引用官方规范和现有工具配置，不默认创建重复的 CODE_STYLE 文档。
- 除必要路径、命令、代码标识符、标准名称和专有名词外，生成内容使用中文。

## 4. 验证初始化结果

- 检查命令和路径确实存在。
- 检查文档没有把尚未实现的行为描述成当前能力。
- 检查 DESIGN 和 ARCHITECTURE 没有重复 README 的使用说明。
- 检查未来 Agent 能在不通读全部文档的情况下找到最小相关资料。
- 明确报告未解决问题和证据缺口。
