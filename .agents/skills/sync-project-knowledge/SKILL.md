# 同步项目知识

每项事实只更新到所属文档，不把文档变成工作日志。

## 1. 阅读文档前先判断影响

根据已完成的变更和最终差异回答：

1. 安装、运行或用户说明是否变化？
2. 项目级必需行为、范围、用户流程或非目标是否变化？
3. 功能级持久行为、验收或规范追溯是否变化？
4. 架构、所有权、数据流、协议、数据结构或不变量是否变化？
5. 是否发现了可能节省未来成本的非显然、项目特有经验？
6. 复杂调查或重大变更是否需要保留证据？

如果全部为否，停止，不修改文档。

## 2. 每项事实只路由一次

- 问题 1 更新 README。
- 问题 2 更新 DESIGN。
- 问题 3 更新对应 Spec；不存在且满足触发条件时使用 `spec-driven-change`，否则不要新建。
- 问题 4 更新 ARCHITECTURE。
- 问题 5 更新 LEARNING。
- 问题 6 使用 `track-change-trace` 在当天 `docs/traces/YYYY-MM-DD.md` 中建立或完成对应任务编号。

每日任务日志由 `record-task-log` 单独追加，不属于知识同步，也不能代替上述文档。

创建新文档类型或目标可能重叠时，先阅读 [references/writing-rules.md](references/writing-rules.md)。

## 3. 精准编辑

- 打开长文档前，先搜索受影响标题或关键词。
- 保持无关内容和格式不变。
- 概述文档描述当前系统，并删除已过期说法。
- DESIGN 只保存项目级目标和整体行为；功能级稳定规范 ID、验收与追溯更新到对应 Spec。
- 计划在实现验证前必须明确标注为计划。
- 链接 TRACE 证据，不把过程复制到 DESIGN 或 ARCHITECTURE。
- LEARNING 条目蒸馏为触发、规则、原因和证据；省略例行事实。
- 文件拆分改变稳定边界或所有权时更新 ARCHITECTURE；项目特有词汇、平台命名例外或非显然注释经验进入 LEARNING，普通重命名和注释不进入概述文档。
- 调研来源和取舍只在会影响未来决策时进入 TRACE；概述文档保留最终事实，不堆积链接和搜索过程。
- TRACE 旧检查点不得被重写；结论变化时追加更正或取代事件，并在最终检查点映射修改前后状态。
- 除必要路径、命令、代码标识符、标准名称和专有名词外，面向人的内容使用中文。

## 4. 一致性检查

- 核对命令、路径、名称、版本和链接。
- 确保 DESIGN 对预期与当前行为的描述一致。
- 确保 ARCHITECTURE 符合真实所有权和数据流。
- 确保 README 没有承诺尚不可用的功能。
- 确保未来调查者能用相关术语搜索到经验条目。
- 只总结实际发生变化的文档。
