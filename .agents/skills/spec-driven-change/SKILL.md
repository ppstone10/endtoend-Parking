# 按需规格驱动变更

Spec 说明某项行为“必须是什么”，任务 TRACE 说明一次修改“如何演进”。不要让两者互相复制。

## 1. 判断是否需要 Spec

- L2 默认不创建。已有 Spec 时只读取相关条目；只有缺陷暴露了可复用的缺失不变量、冲突预期或反复回归时才新增或修订。
- L3 新增或改变用户可观察行为、需要跨会话验收，或实现包含多个可独立交付步骤时，使用轻量 Spec。
- L4/L5 涉及公共契约、数据结构、协议、迁移、安全、隐私、权限、多客户端一致性或长期分阶段交付时，使用完整 Spec。
- 纯内部且行为不变的重构由 DESIGN、ARCHITECTURE 和测试约束即可说明时，不为形式创建 Spec。

## 2. 只加载相关契约

- 先按任务关键词搜索 `spec/`、DESIGN、测试名和公共接口，只读取直接相关条目。
- 项目已有 Spec 结构和命名时沿用；没有时复制 [assets/SPEC.template.md](assets/SPEC.template.md) 到 `spec/<feature>.md`。
- 一个功能或领域一份 Spec；规模增长时按领域分目录，禁止建立需要每轮通读的全仓巨型追溯表。
- Spec 是当前行为契约，不保存调研过程、命令流水或任务时间线。

## 3. 选择规格强度

- **轻量：** 保留目标、非目标、边界、稳定规范 ID、可观察行为、验收和就近追溯；删除不适用的完整档章节。
- **完整：** 额外定义数据/状态、接口、异常与恢复、兼容/迁移、回退、安全/隐私和分阶段状态。
- 规范 ID 使用 `<DOMAIN>-<TOPIC>-<NNN>`，例如 `AUTH-SESSION-001`。进入追溯后保持稳定；废弃时保留 ID 和原因，不复用编号。

## 4. 在实现前建立可验收契约

- 用用户或系统可观察结果描述行为，不预先锁死没有必要的内部实现。
- 为正常、边界、错误和恢复路径定义本次范围内的验收。
- 在同一 Spec 的“追溯”表预留规范 ID，初始状态为 `⏳`；记录预计测试或人工验收入口，允许实现位置暂写“待补”。
- 只有未解决选择会改变行为、范围、风险、迁移或验收时才向用户确认；仓库已有权威答案时直接采用。

## 5. 让证据与任务类型相称

- 新行为可自动化时，优先在实现前编写验收或回归测试，并确认它因目标行为缺失而失败。
- 修复既有缺陷时优先增加能复现根因的回归测试，但不得为了展示红灯回退用户改动或重建高成本旧环境。
- 行为不变的重构记录修改前后同一组测试通过，不制造必然失败的测试。
- 无法自动化时写明可重复的人工验收步骤和原因，不把“未执行”标为通过。
- 测试名称、实现符号和命令使用稳定定位；行号只能作为辅助。

## 6. 实施并保持 Spec 领先

- 只实现当前 Spec 和任务范围要求的行为。
- 发现契约缺口或方案改变了可观察行为时，先更新 Spec 与追溯状态，再继续实现。
- 任务 TRACE 需要记录方案演进时引用规范 ID，不复制整份 Spec。
- 可用 `python3 .agents/skills/spec-driven-change/scripts/check_spec.py <spec-file> [...]` 检查本轮涉及的 Spec；不得默认扫描全部历史 Spec。

## 7. 完成追溯

- 将每个规范 ID 映射到验收、测试或人工入口、实现符号和实际验证。
- 状态只使用：`⏳` 待完成、`✅` 证据完整、`⚠️` 部分完成或有风险、`🚫` 明确不实施。
- 只有测试/实现/验证证据完整且没有未披露缺口时标记 `✅`。
- 部分完成、推迟或拒绝的内容保留原因和责任边界；worklog 只引用规范 ID 和结果，不复制追溯表。
