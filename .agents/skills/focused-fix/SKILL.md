# 精准修复

把成本花在缺陷上，而不是流程仪式上。

## 1. 锁定范围

- 用一两句话说明实际行为和预期行为。
- 从报告、日志、失败测试或直接复现中确定最窄受影响范围。
- 不通读所有概述文档。只有某文档负责预期行为或相关不变量时才读取对应部分。
- 项目在该领域存在历史经验时，才按相关关键词搜索 `LEARNING.md` 和 trace 文件名。
- 只有相关 Spec 已存在或预期行为发生冲突时，才按关键词读取对应规范条目；不得通读全部 `spec/`。

## 2. 证明根因

- 条件允许时复现失败；无法复现时寻找直接代码证据。
- 沿症状到状态修改或边界失败的最短路径追踪。
- 修改前提出可被证伪的根因假设。
- 区分问题源头与症状显现位置。
- 第一轮定向调查后根因仍不明确时，才阅读 [references/diagnosis-guide.md](references/diagnosis-guide.md)。
- 调查出现多个被证伪假设、跨越重要边界或需要保留方案演进时，加载 `track-change-trace` 建立追加式轨迹；普通局部缺陷不创建。

## 3. 应用最小充分修正

- 在问题所属层修复根因。
- 保持周边架构、控制流形态、命名和无关格式不变。
- 只有误导名称或失效注释直接妨碍根因修复，且修改保持在触达范围内时才同步修正；跨文件、公共符号或结构整理必须升级或另开任务。
- 新增辅助方法、抽象、选项或依赖前，先复用现有机制。
- 不修复相邻问题；有价值时单独报告。
- 不得通过吞掉错误、关闭行为、削弱契约或引入无依据默认值来掩盖缺陷。

如果修复需要改变公共契约、数据库或数据结构、依赖、权限、隐私、安全、迁移、核心状态所有者或跨系统行为，继续前必须升级到 `full-development`。

如果缺陷暴露了可复用的缺失不变量、冲突预期或反复回归，升级后加载 `spec-driven-change` 补充轻量或完整 Spec；普通局部缺陷不创建 Spec。

## 4. 一次性按比例验证

- 优先增加能针对原始根因失败的回归测试。
- 运行能覆盖修改行为并编译修改范围的最小检查。
- 后续更广命令已覆盖更窄命令时，不重复运行后者。
- 只有变更或证据表明影响更广时才扩大验证。
- 准确记录实际运行内容和剩余缺口。

## 5. 只保留有价值的知识

- README、DESIGN 或 ARCHITECTURE 中的当前事实变得不正确时才更新。
- 只有复杂调查证据未来仍有价值时才创建 TRACE，并按当天文件追加基线、重要调整和最终变更映射。
- 经验同时满足项目特有、非显然、可复用且可能避免未来浪费时，才加入 LEARNING。
- 只有满足上述任一条件时才调用 `sync-project-knowledge`。

## 6. 轻量收尾

- 复用上述根因、差异和定向验证证据，不为收尾重复运行命令。
- 确认缺陷已解决、没有无关修改，且无需升级工作流。
- 修改代码、测试、脚本、构建配置、数据结构或协议后，在最终答复附上建议 Commit 标题和必要正文，不自动提交或推送。
