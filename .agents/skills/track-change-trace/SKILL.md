# 跟踪修改轨迹

TRACE 跟踪“修改如何演进以及为什么”，worklog 只索引“任务何时执行以及结果如何”。两者不得互相复制。

## 1. 建立轨迹

- 使用任务开始时间生成稳定编号 `T-HHmmss`；同日编号冲突时追加短序号。
- 在 `docs/traces/YYYY-MM-DD.md` 底部建立 `## T-HHmmss · Lx · 任务名`。当天文件存在时只查看末尾必要范围后追加，禁止把最新任务放到文件顶部。
- 开始检查点记录时间、状态“进行中”、修改前基线、目标状态、已知边界和预计影响范围。
- L4/L5 必须在实施实质修改前建立；L2/L3 只有根因复杂、方案会演进或跨越多个重要范围时建立。

## 2. 追加重要检查点

只在下列事件发生时追加 `### HH:mm:ss · 类型`：

- 证据否定原假设或根因发生变化；
- 用户边界、验收条件或授权发生变化；
- 方案、契约、数据形态、迁移、回退、安全或隐私处理发生实质调整；
- 影响范围升级或发现必须保留的外部依赖；
- 验证结果迫使实现发生变化。

检查点写清“原计划或原状态 → 新计划或新状态”、原因、受影响范围和证据。不得重写旧检查点；错误或过期结论用新的“更正”或“取代”事件说明。

同一天较早任务在后续任务已经出现后重新继续时，不回到上方任务块插入当前时间。应在文件底部追加 `## 同一任务编号 · 继续`，再写新检查点并链接原任务块，保持全文从旧到新。

## 3. 完成变更映射

结束时追加最终检查点：

- 明确状态：完整完成、部分完成、受阻或仅完成诊断；
- 按组件或文件说明“修改前 → 修改后”，以及修改原因；
- 标明已完成、取消、推迟和超出范围的内容；
- 映射验证覆盖与未验证缺口；
- 链接受影响的 README、DESIGN、ARCHITECTURE、LEARNING、决策记录和 worklog；
- 已启用 Spec 时引用受影响规范 ID 和对应文件，不复制追溯表；
- L4/L5 记录契约、迁移、回退、恢复、安全和隐私的最终状态。

## 4. 控制成本与边界

- 不记录搜索命令、文件读取、工具调用、完整差异、原始日志或逐步思考。
- 没有实质调整时只保留开始和完成两个检查点。
- 一个自然日只有一个 TRACE 文件，但可包含多个任务编号；跨日任务在新日期文件追加同一编号的“继续”检查点并链接前一日。
- 同一日期文件自上而下按可恢复的真实时间从旧到新排列；`时间未记录` 的历史迁移块放在已知时间任务之前。顺序修复可以移动完整任务块，但不能改写其中事实。
- TRACE 是追加式证据，不是当前事实来源。最终事实仍更新到对应概述文档，可复用经验进入 LEARNING。
- worklog 用同一任务编号链接 TRACE；TRACE 不复制 worklog 的时间摘要和交付总结。
